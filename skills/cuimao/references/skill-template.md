# 技能包模板与 description 写作指南

## 一、文件结构

一个技能一个文件夹，文件夹里只有一个 `SKILL.md`：

    技能包/
    ├── <name-1>/
    │   └── SKILL.md
    └── <name-2>/
        └── SKILL.md

文件夹名必须跟 `name` 字段完全一致。`技能包/` 根目录下不许出现任何散文件。

## 二、SKILL.md 骨架

**文件第一行必须是三个减号**，前面不能有空行、标题或任何其他字符。下面代码块里的第一行三个减号是文件内容的一部分，必须原样写进去，它不是代码块边界。

```
---
name: <内容简称>-<技能主题>
description: <60到120字，写法见下>
---

# <技能中文名>

## 什么时候用它

<具体的问题场景，用用户会说的话描述>
<如果需要先用另一个技能，在这里写明，并且同一句必须也出现在 description 里>

## 核心判断

<一到三句，有立场的主张>

## 怎么做

1. <可执行的动作>
2. <可执行的动作>
3. <可执行的动作>

## 判断标准

做对了会看到：<可观察的信号>

做错了会看到：<可观察的信号>

## 什么时候不该用它

<失效场景，来自骨架的盲点与边界。不能写"无"。>

## 出处

来自《<内容标题>》<章节或时间点>

原文：<一句摘录>
```

## 三、name 字段

- 小写英文或拼音，只用连字符连接
- 不要中文、空格、下划线
- 长度不超过 64
- 必须带内容简称前缀，否则蒸馏第二本书时会撞名
- **必须跟所在文件夹名完全一致**

中文技能名写在正文的一级标题里，不要写进 `name`。

## 四、description 字段

这是决定技能能不能被正确触发的唯一字段，也是宿主唯一会常驻扫描的内容。正文是触发之后才加载的，所以**任何影响"该不该触发我"的信息，都必须出现在这里**。

规则：

- 控制在 60 到 120 字
- 写"什么情况下用"，不是"这个技能是什么"
- 用用户会真实说出口的词，不要用书里的术语
- 必须写明什么情况下不要用它
- 如果有前置技能，在这里点名

写得差的：

> 本技能基于第一性原理提供业务决策框架，帮助用户进行战略判断。

全是抽象名词，用户不会这么说话，也没有排除条件，会乱触发。

写得好的：

> 当用户在纠结一个新业务、新项目、新方向该不该做，要不要投入，值不值得干的时候使用。会给出一套判断该不该做的检查清单。已经决定要做、只是问怎么做的情况，不要用这个技能。

## 五、除了这两个字段，别的都不要写

不要写 `allowed-tools`、版本号、作者。这类技能是纯方法，不需要任何工具权限，留空等于最小权限，导入时更容易通过安全审查。

## 六、写完必须自检一条

把"出处"那一段遮住，重读这个技能。它读起来像什么？

- 像"这本书第 X 章讲了什么" → **失败，重写**
- 像"遇到这个问题时，一步步该怎么办" → 合格

这是最容易滑过去的失败模式。内容本身往往一章一个主题，顺着写下来，产出会不知不觉变成章节摘要——看着挺全，实际没法用。技能是拿来用的，不是拿来读的。
